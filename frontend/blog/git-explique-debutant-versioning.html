Git & GitHub Débutant Pro Clean Code Sans le Seum

Si tu as déjà cherché à comprendre ce qu'est Git sur Google ou Wikipédia, tu es sans doute tombé sur une définition du style :

"Git est un logiciel de gestion de versions décentralisé permettant d'enregistrer et de tracer l'évolution d'un ensemble de fichiers informatiques dans un graphe acyclique dirigé."

Et là, tu as refermé ton navigateur en te disant : "OK, merci, je n'ai absolument rien compris."

Alors on va reprendre tout ça depuis zéro. Sans jargon élitiste, sans formules mathématiques inutiles, avec des analogies de la vraie vie, en commençant par le pourquoi avant de parler de la moindre commande technique.

Le problème universel que Git vient résoudre

Imagine que tu travailles sur ton premier site web. Tu crées une page d'accueil, elle s'affiche correctement, le design te plaît. Et là, tu as envie de tenter un truc plus complexe : modifier les couleurs, tester une mise en page différente avec CSS Grid.

Tu modifies ton code, tu testes... et là, catastrophe : tout est cassé. Le menu a disparu, les blocs se superposent n'importe comment, et tu ne sais plus du tout ce que tu as changé par rapport à 10 minutes plus tôt.

Tu veux faire Ctrl + Z, mais tu as déjà fermé ton éditeur. Ton ancienne version qui marchait si bien n'existe plus. Elle a été écrasée.

Pour éviter ce cauchemar, tout le monde est passé par cette méthode artisanale et chaotique :

  • projet-site.html
  • projet-site-v2.html
  • projet-site-VRAIMENT-FINAL.html
  • projet-site-version-qui-marche-enfin.html

Ton bureau se retrouve envahi de 15 fichiers presque identiques, et tu es incapable de savoir lequel est le bon.

Git est né pour tuer cette pagaille. C'est tout simplement une machine à voyager dans le temps pour ton code. Il enregistre l'état exact de tes dossiers à des moments choisis, proprement, automatiquement, et te permet de revenir en arrière d'un claquement de doigts.

L'analogie qui fait tout comprendre : la sauvegarde de jeu vidéo

Pense à Git exactement comme au système de sauvegarde d'un jeu vidéo RPG (comme Pokémon, Zelda ou The Witcher).

Dans un jeu, tu sauvegardes ta partie avant d'affronter un boss difficile. Si ton personnage est éliminé, tu ne recommences pas le jeu depuis le début : tu recharges ta sauvegarde précédente et tu réessaies avec une stratégie différente. Tu peux aussi garder plusieurs emplacements de sauvegarde pour rejouer un passage mémorable.

Git fonctionne de la même manière pour tes projets web. Chaque "point de sauvegarde" porte un nom : un commit. Tu travailles, tu écris du code, et dès que tu atteins une étape qui fonctionne proprement, tu crées un commit.

Si demain tu introduis un bug en voulant tester une fonctionnalité, tu peux faire revenir ton projet à l'exact état d'hier matin à 10h42.

Les trois mots indispensables à retenir

Dans le monde Git, il y a trois termes fondamentaux que tout le monde confond au début :

  1. Le Repository (ou "Repo") : c'est tout simplement le dossier de ton projet sur ton ordinateur, mais sous surveillance active de Git. Quand tu actives Git dans ton dossier, Git crée un dossier invisible (.git) qui va mémoriser l'historique complet de toutes tes modifications.
  2. Le Commit : c'est ta sauvegarde scellée dans le temps. C'est une photographie instantanée de tous tes fichiers. Chaque commit est accompagné d'un message rédigé par tes soins décrivant ce que tu as accompli (par exemple : "Création du formulaire de contact").
  3. La Branch (Branche) : imagine que tu veuilles tester une idée un peu folle (changer complètement la charte graphique de ton site) sans risquer de bousiller ta version stable. Une branche te permet de créer un univers parallèle. Tu t'amuses sur ta branche test. Si le résultat est génial, tu fusionnes ta branche avec ta version principale ; si c'est raté, tu la supprimes sans que ta version principale n'ait été touchée.

Git et GitHub : la confusion n°1 clarifiée

Attention, beaucoup de débutants croient que Git et GitHub sont la même chose. C'est faux :

  • Git est un logiciel : il est installé localement sur ton ordinateur. Il n'a même pas besoin d'une connexion internet pour fonctionner. Il gère tes sauvegardes et ton historique hors ligne.
  • GitHub est un service web dans le cloud : c'est une plateforme en ligne (rachetée par Microsoft) qui te permet d'héberger une copie de ton repository Git sur internet.

Pourquoi envoyer ton code sur GitHub ? Pour trois raisons majeures :

  1. La sauvegarde externe : si ton ordinateur portable tombe par terre ou rend l'âme, tout ton historique de travail est en sécurité sur les serveurs de GitHub.
  2. Le travail en équipe : deux développeurs peuvent travailler sur le même projet à distance sans s'envoyer des fichiers zip par email ou sur Discord.
  3. Ton portfolio public : pour un recruteur ou un client, ton profil GitHub est souvent plus important que ton CV. Il permet de voir si tu écris du code propre et si tu sais travailler avec les outils du métier.

Les 6 seules commandes dont tu as besoin au début

Il existe des dizaines de commandes Git avancées (rebase, cherry-pick, stash...), mais au début, tu n'as besoin que de ces six-là pour faire 95% de ton travail :

1. Initialiser le projet

git init

À lancer une seule fois dans le dossier de ton projet pour dire à Git : "Commence à observer ce dossier."

2. Vérifier l'état de tes fichiers

git status

La commande réflexe. Git t'affiche la liste des fichiers modifiés, créés ou supprimés depuis ta dernière sauvegarde.

3. Préparer les fichiers à sauvegarder

git add .

Le point signifie "tout ajouter". Tu déposes tes fichiers modifiés dans le sas de chargement (le staging) avant de valider la photo.

4. Créer la sauvegarde officielle

git commit -m "Ajout de la section avis clients"

C'est ici que tu déclenches la photo. Le message entre guillemets doit résumer clairement ce que tu as accompli.

5. Envoyer sur GitHub

git push

Envoie tes commits locaux vers ton compte GitHub pour mettre à jour la version en ligne.

6. Voir la liste de tes sauvegardes

git log --oneline

Affiche ton carnet de bord : chaque commit sur une ligne avec son identifiant court et son message.

Une vraie session de travail avec Git pas à pas

Concrètement, comment se déroule une session de code avec Git au quotidien ?

Tu allumes ton PC, tu ouvres VS Code (si ton éditeur n'est pas encore prêt, consulte notre guide : Mon setup VS Code pour débuter sans plugins inutiles). Tu ajoutes un nouveau bouton dans ton fichier index.html et tu règles sa couleur dans style.css. Tu testes dans ton navigateur : tout s'affiche à la perfection.

Tu ouvres alors le terminal intégré de VS Code (raccourci Ctrl + `) et tu déroules le rituel en 15 secondes chrono : 

git status
# → Git te confirme : 2 fichiers modifiés (index.html et style.css)

git add .
# → Tu prépares tes fichiers

git commit -m "Ajout du bouton d'inscription hero"
# → Ta sauvegarde est enregistrée localement

git push
# → C'est synchronisé sur GitHub en toute sécurité !

Ce cycle devient une seconde nature au bout de deux jours d'utilisation.

À quelle fréquence faut-il faire un commit ?

C'est une des questions les plus fréquentes chez mes apprenants. Il n'y a pas de compteur fixe, mais voici la règle d'or d'un ingénieur senior :

Fais un commit chaque fois que tu as terminé une petite unité de travail qui fonctionne. Ne commite jamais du code cassé qui fait planter ton site, et n'attends pas la fin de la semaine pour tout sauvegarder d'un bloc.

Une astuce simple : si tu es capable de décrire en une phrase simple ce que tu viens de faire ("J'ai centré le logo", "J'ai réparé le lien du menu", "J'ai créé le pied de page"), c'est le moment idéal pour faire un commit.

Pourquoi Git fait peur aux débutants (et pourquoi c'est normal)

Si Git impressionne autant les débutants, ce n'est pas parce que le principe est complexe : c'est parce qu'il s'utilise majoritairement dans un terminal en ligne de commande avec un écran noir et du texte blanc.

Pour beaucoup de gens qui n'ont jamais manipulé que des souris et des fenêtres graphiques, taper des commandes dans un terminal donne l'impression d'être un hacker dans un film des années 90, avec la peur panique d'effacer son disque dur par erreur.

Et les messages d'erreur de Git (comme fatal: not a git repository ou Your branch is ahead by 1 commit) ont l'air très martiens quand on ne connaît pas encore le vocabulaire.

Mais rassure-toi : après 3 heures de pratique guidée sur un vrai projet, la peur du terminal s'évapore complètement. Taper git status devient aussi naturel que faire un double-clic sur un dossier.

Tout comme la fausse idée selon laquelle il faudrait être bon en maths pour coder, la peur de Git et du terminal repose sur un malentendu. Avec la bonne méthode et un accompagnement bienveillant, chaque commande prend tout son sens.

Ce que ton GitHub dit de toi aux recruteurs

Voici une histoire vraie que je raconte souvent : un de mes anciens élèves en reconversion n'avait aucun diplôme d'informatique, pas même un bac scientifique.

Lors de son premier entretien pour un stage de développeur front-end, il n'a pas sorti un CV classique. Il a ouvert son profil GitHub. Le recruteur a pu explorer ses repositories : l'historique des commits était régulier, les messages étaient clairs, le code était propre et structuré.

Le recruteur a vu en 2 minutes que le candidat savait déjà travailler avec les mêmes méthodes professionnelles que son équipe en poste. Il a décroché son stage sur le champ.

Git et GitHub ne sont pas de simples outils de stockage : ce sont les preuves tangibles de tes compétences et de ta rigueur.
